# UTFR Firmware Tutorials

Onboarding material for the University of Toronto Formula Racing firmware
team, built on the same stack the real firmware (github.com/UTFR/firmware)
uses: real STM32G4 HAL calls, real FreeRTOS, the same hand-rolled CMake build
system, and the same bootloader, targeting the same chip the team's actual
controllers use, the STM32G474RET6.

This is not a simplified/Arduino stand-in. If you can build and flash the
boards here, you already know most of what you need to build and flash the
real controllers.

## Toolchain

You need `cmake` and `ninja`. We target a Cortex-M4F, so you need
`arm-none-eabi-gcc` and the associated GNU tools (`ld`, `ar`, etc.). We also
require `clang-format` (configure your editor to format on save so diffs
never carry formatting-only changes).

`clangd` is optional but recommended for editor intellisense.

For flashing, install `STM32CubeProgrammer` and put `STM32_Programmer_CLI` on
your `$PATH` -- then the `flash` CMake target works without going through the
GUI. `STM32CubeMX` isn't necessary to work with this repo (none of this is
CubeMX-generated), but it's a fine way to poke around STM32 HAL/peripheral
config if you're curious.

## Building

```bash
cmake --preset firmware
cmake --build --preset firmware
```

`can.cmake` and `git.cmake` need the packages in `scripts/requirements.txt`
(`cantools`, `PyYAML`). `cmake/python.cmake` checks whether your system
`python3` already has them and provisions a venv in `scripts/.venv`
automatically on first configure if not.

## Boards

Three targets, each a normal per-board CMake project under `controllers/`,
same pattern the real controllers (`ACM`, `FC`, `RC`, ...) use:

- **`LECTURE2_CONCURRENCY`** -- race conditions on bare metal. No RTOS: the
  "two concurrent flows of control" from the lecture are a real
  mainline-vs-timer-ISR race on shared, non-atomic state. See
  `controllers/lecture2_concurrency/`.
- **`LECTURE3_FREERTOS`** -- the same problem, now with the real FreeRTOS
  kernel (the exact one vendored into the real firmware repo): tasks,
  mutexes, queues, software timers, task notifications. See
  `controllers/lecture3_freertos/`.
- **`INTRO_PROJECT`** -- the onboarding assignment: a simplified EV state
  machine (LV -> TS -> RTD) with real GPIO/ADC/SPI/CAN peripheral access
  provided via a small board-support layer (`bsp.h`/`bsp.c`), and an empty
  `app_main()` for you to fill in with the actual concurrency architecture.
  Read `controllers/intro_project/src/intro_project.c` for the full
  assignment.

Several lecture files can't all link into one executable at once (they
redefine the same functions as alternate takes on the same problem -- e.g.
a mutex-based fix vs. a queue-based fix). The "active" one is in each board's
`CMakeLists.txt`'s `*_SRC` list; the others are compiled as separate,
non-linked `OBJECT` library targets (so they're still proven to build against
the real headers) -- swap one into `*_SRC` in place of the active file to try
it for real.

## Flashing

Each board needs the bootloader (`BOOTLOADER_STM32G474`) flashed once, then
its app image can be reflashed independently:

```bash
cmake --build --preset firmware --target BOOTLOADER_STM32G474
# flash BOOTLOADER_STM32G474.elf once via STM32CubeProgrammer or the `flash` target

cmake --build --preset firmware --target INTRO_PROJECT
# flash INTRO_PROJECT.elf the same way, as many times as you want
```

## Organization

`controllers/<board>/` is a self-contained CMake project per board, just like
the real firmware repo. `common/` holds libraries shared across boards
(vendored STM32G4 HAL, CMSIS, FreeRTOS, and thin per-peripheral wrapper
libraries like `UTFR_CAN`, `UTFR_UART`, `UTFR_DIGITAL`) -- these are the same
files vendored in the real firmware repo, not a stripped-down teaching
version. `bootloader/` is the same shared bootloader the real controllers
boot from. `cmake/` is the build machinery: per-MCU descriptors
(`cmake/mcu/stm32g474.cmake`), the generic HAL module system
(`cmake/hal.cmake`), and the board declaration helpers (`cmake/board.cmake`).

Each board needs a HAL and FreeRTOS config; those live in `include/hal/` per
board (`config.h`, mainly `INTERRUPT_PRIORITY`). Because config can differ
per board, common libraries are compiled once per board via
`utfr_declare_lib`/`utfr_instantiate_lib` (see `cmake/board.cmake`), suffixed
with the board name -- so you get `UTFR_LOGGING-LECTURE3_FREERTOS`,
`UTFR_LOGGING-INTRO_PROJECT`, etc. Take care to link the correctly-suffixed
target.

## Autogen

`UTFR_CAN` depends on message types autogenerated from the DBC files in
`dbc/` (a trimmed set -- `front`/`rear`/`inverter` -- copied from the real
repo, kept only so the generated headers `UTFR_CAN` needs actually exist).
`INTRO_PROJECT`'s steering-angle CAN message isn't a real DBC message; it's a
hand-picked CAN ID handled directly in `bsp.c`, since inventing a new DBC
entry isn't the point of the assignment.

## Contributing

Same conventions as the real firmware repo: format with `clang-format` before
committing (CI's `format` job will catch anything you miss), and for the
`intro_project` assignment specifically, follow the submission instructions
in `controllers/intro_project/src/intro_project.c`.
